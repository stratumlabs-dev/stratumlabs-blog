Resolving Terraform State Lock Failures and Concurrent Apply Conflicts

By Stratum Labs (contact.stratumlabs@gmail.com)

When multiple engineers or automated CI/CD pipelines attempt to modify cloud infrastructure simultaneously, Terraform uses state locking (typically via DynamoDB when using an S3 backend) to prevent conflicting writes. However, if a pipeline crashes or an apply job hangs, your state can remain locked indefinitely, blocking all subsequent updates.

Understanding State Locks

A state lock ensures that only one process can run an apply against a specific state file at a time. When a lock fails or gets orphaned, you will typically see an error resembling this:

Error: Error acquiring the state lock

Error message: State locked by another Terraform command
Lock Info:
  ID:        12345678-abcd-1234-abcd-123456789abc
  Path:      my-terraform-bucket/prod/terraform.tfstate
  Operation: TypeApply
  Who:       runner@i-0123456789abcdef0
  CreatedAt: 2026-10-16 02:10:00.123456789 +0000 UTC
  TTL:       0

Terraform acquires a state lock to protect the state-file from being written
to by multiple concurrent processes at the same time. Please resolve the
issue above and try again. If you are certain no other Terraform command
is running, you can force-unlock the lock using the 'terraform force-unlock' command.

Safe Resolution Steps

Before blindly forcing a unlock, you must verify that no other CI/CD job or team member is actively running an apply.

  • Step 1: Check Active Pipelines: Inspect your GitHub Actions, GitLab CI, or Jenkins build history to ensure no jobs are currently hung or running.
  • Step 2: Force Unlock (When Safe): If you are certain the process is dead, use the Lock ID provided in the error message to clear the lock:
terraform force-unlock 12345678-abcd-1234-abcd-123456789abc

Preventing Future Conflicts

To minimize concurrent apply collisions in team environments:

  • Enforce strict PR checks so infrastructure changes are applied sequentially through a centralized CI/CD runner rather than local developer machines.
  • Implement short timeouts and proper error handling in your pipeline workers so crashed runners release locks automatically.

Summary

State lock errors can be frustrating bottlenecks, but understanding how remote backends manage locks allows you to safely clear orphaned processes and restore pipeline velocity without risking state corruption.
